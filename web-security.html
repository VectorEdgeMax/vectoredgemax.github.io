Web Security: Learn and Test Responsibly

Study HTTP, browser security, authentication, common vulnerabilities, secure development and a structured testing process.

Study in order, practise in a lab you own or have explicit permission to test, take notes, and revisit each level. Examples are educational; never run security tests against systems without authorization.

Level 1 — Web foundations

Understand browsers, servers, DNS, HTTP requests/responses, methods (GET, POST, PUT, DELETE), status codes, headers, cookies, sessions, HTML, JavaScript, APIs and databases. HTTPS protects transport but does not make a vulnerable application safe.

Level 2 — Identity and session safety

  • Use secure password hashing (Argon2id, scrypt or bcrypt via trusted libraries), MFA and rate limits.
  • Use secure, HttpOnly and appropriate SameSite cookie attributes; rotate sessions after login and privilege changes.
  • Implement server-side authorization on every protected action, not just hide UI buttons.
  • Use short-lived tokens, safe storage, rotation and revocation appropriate to the architecture.

Level 3 — Common weakness classes

Injection

Untrusted input becomes part of a query or command. Use parameterized SQL, avoid shell concatenation, and validate inputs.

Cross-site scripting (XSS)

Untrusted content executes in a browser context. Use context-aware output encoding, safe DOM APIs and a suitable Content Security Policy.

Broken access control / IDOR

Users access another user's resource by changing an identifier. Verify ownership and permissions server-side on every request.

CSRF

A browser is tricked into submitting an unwanted authenticated action. Use CSRF tokens and SameSite cookies, and avoid state changes on GET.

SSRF

A server is induced to make unintended requests. Restrict destinations, validate resolved IPs, block metadata/internal ranges and use egress controls.

Misconfiguration and vulnerable components

Remove debug endpoints, patch dependencies, protect secrets, set safe headers and limit unnecessary services.

Level 4 — Defensive implementation examples

Parameterized SQL (Python sqlite3)

cursor.execute(
    "SELECT id, display_name FROM users WHERE email = ?",
    (email,)
)

Do not build SQL by concatenating user input. Placeholder syntax differs by database driver.

Safer HTML rendering

Prefer framework template engines that escape by default. Do not insert untrusted text using raw HTML APIs. Sanitization and output encoding are different tasks.

Level 5 — Testing workflow

  1. Define written scope and test accounts; use staging or a training app.
  2. Map routes, roles, input points, APIs and data flows.
  3. Test authentication, authorization, session management, input validation, error handling, business logic, cryptography and client-side behavior.
  4. Use passive observation first; only perform active tests that are explicitly permitted.
  5. Record evidence with secrets redacted, severity, impact, reproducible steps and remediation.
  6. Fix, retest and close findings.

Level 6 — Tools and learning

Browser DevTools, OWASP ZAP, Burp Suite Community, dependency scanners and code analyzers are useful in an authorized environment. Start with deliberately vulnerable training apps and the OWASP Web Security Testing Guide, which organizes testing across information gathering, configuration, identity, authentication, authorization, sessions, input validation and more.

Secure release checklist

  • Threat model important flows and trust boundaries.
  • Use least privilege and server-side authorization checks.
  • Validate inputs and encode outputs by context.
  • Protect secrets and use maintained dependencies.
  • Set TLS, security headers, logging, backups and incident response.
  • Run tests in CI and retest findings before release.
